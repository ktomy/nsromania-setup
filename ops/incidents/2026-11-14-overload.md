# Incident: production overload and MongoDB starvation (2026-11-14/15)

| | |
| --- | --- |
| Status | Resolved (mitigated); capacity follow-ups open |
| Impact window | 2026-11-14 ~15:00 UTC to 2026-11-15 ~22:05 UTC (about 31 hours) |
| Host | `nsromania.info` (8 vCPUs, 62 GiB RAM, 8 GiB swap, KVM VPS) |
| Affected | All ~416 hosted Nightscout instances and the setup panel (`setup.nsromania.info`) |
| Data loss | None |

All times are UTC. This repository is public: the note gives counts only. Instance lists are in the root-only backups
listed at the end.

## Summary

The host has very little spare capacity. Our own load is about 62% CPU, and RAM plus swap were full. When the
hypervisor's CPU steal doubled from about 10% to about 20% on 2026-11-14, the remaining headroom disappeared. MongoDB,
which competed thread-by-thread with about 400 Node processes, was starved of CPU. Its latency then started a
self-sustaining loop of driver pool clears, reconnects and uploader retries, and the load rose from about 15 to
300–450.

A latent defect amplified the loop. Nightscout 15.0.7 closes pooled MongoDB connections after 30 s idle but reloads
its data every 60 s. So every instance re-authenticated 4–5 connections every minute: about 1,400 SCRAM-SHA-256 logins
per minute in total, around the clock.

The incident was resolved by:

- giving mongod CPU priority;
- setting a 10-minute pool idle time on every instance;
- restarting all instances once, which broke the loop and released accumulated memory;
- removing 37 orphaned or unused instances.

## Impact

- Nightscout sites were slow or unavailable. In a sample of instance traffic on 2026-11-15, about 11% of requests
  ended with HTTP 499 (client gave up) and about 10% with HTTP 502. Uploads were retried; POST volume was about 50%
  above normal.
- The setup panel was very slow, especially on per-domain pages. These open a new MongoDB connection per call, list
  all databases and read the full PM2 process list; PM2 itself took minutes to answer.
- MongoDB slow operations: about 1,000 per minute, median 0.9 s, p95 about 10 s. Even `hello`/authentication steps
  were slow.
- Memory: 3 GiB available; swap filled completely, putting mongod (the largest process) at risk from the OOM killer.

## Root cause analysis

### 1. Insufficient headroom (underlying condition)

- About 416 Nightscout instances, at about 1.5% CPU each, used about 62% of 8 vCPUs before the incident. Idle CPU
  averaged about 21%.
- Instances held 54 GiB of RAM plus swap (median 138 MB each); mongod had 8 GiB (its WiredTiger cache). Before the
  2026-11-13 restart, swap had been 100% used for days. Instance memory grows slowly until the host is full.
- The instance count grew from 355 (August) to 416.

### 2. Trigger: hypervisor CPU steal doubled

Steal is CPU time our vCPUs wanted but the hypervisor gave to something else.

| Day | user | steal | idle |
| --- | --- | --- | --- |
| 11-10 to 11-13 | ~62% | 9–12% | ~21% |
| 11-14 | 65% | 19% | 11% |
| 11-15 (to 15:00) | 74% | 18% | 3% |

The provider's backups ran every 6 hours. They are now weekly, but steal stayed at 15–20% afterwards, with 5-second
bursts above 50%. Noisy neighbours or host overcommit are likely contributors.

### 3. Amplifier: mongod scheduled as one of about 400 equal processes

Both mongod (`mongod.service`) and all instances (`pm2-root.service`) are in `system.slice`. No unit set a CPU weight,
so the cgroup v2 `cpu` controller was not enabled inside `system.slice`. mongod therefore competed thread-by-thread with
about 400 Node processes and, under saturation, got a tiny share of CPU.

- Its latency caused MongoDB driver heartbeat timeouts and `MongoPoolClearedError`, so instances reconnected.
- Requests piled up, and uploaders and browsers retried.

All of this added load and kept the host saturated, even when steal dipped.

### 4. Amplifier, latent and permanent: Nightscout pool idle timeout shorter than its reload interval

- `lib/storage/mongo-storage.js` (v15.0.7) creates its client with `maxPoolSize: 5`, `minPoolSize: 0` and
  `maxIdleTimeMS: 30000`. The driver default is 0, so the 30 s comes from Nightscout.
- `lib/bus.js` emits `tick` every 60 s. On each tick, `bootevent.js` reloads data with about 14 parallel queries, using
  the whole pool.
- Between ticks the pooled connections sit idle for about 60 s, longer than 30 s. At the next checkout the driver
  destroys them as `idle` and opens new ones, each with a full SCRAM-SHA-256 authentication.
- Measured: each instance made a burst of 4–5 logins exactly 60 s apart, about 1,390 logins/min in total, with about
  1,300 sockets in TIME_WAIT. Quiet instances churned the most: about 40 logins per 10 minutes, against about 2 for the
  busiest one.

This existed before the incident and consumed CPU on both sides all the time; it was not caused by the overload.

### 5. Contributing: panel per-domain pages

`src/lib/services/nsdatbasea.ts` creates a new `MongoClient` (with a new login) per call and runs `listDatabases`; the
panel also calls `pm2.list` across about 415 apps. These are cheap on a healthy host but very slow on a starved one.

### Not the cause

- Traffic: requests per hour on 2026-11-14/15 were lower than on 2026-11-13.
- Crash loops: no instance was restarting.
- MongoDB queries and indexes: slow operations were indexed queries and even authentication handshakes, which points to
  CPU starvation, not query plans.
- Disk I/O: iowait was about 0%.

## Conclusions

1. **The host runs too close to capacity.** About 66% of CPU is our own steady work. With 10% steal there is about 20%
   headroom; with 20% steal there is almost none, and any spike tips it into the feedback loop. More capacity is
   required: a separate MongoDB server, or splitting instances across hosts.
2. **Steal is now a first-class metric.** It doubled without warning and remains elevated after the backup change.
   Evidence is being collected for the provider (`ops/cpu-steal/README.md`).
3. **Shared databases need scheduling isolation.** With hundreds of busy processes on the host, mongod must not compete
   as a peer. The cgroup CPU weight fixed most of the database latency within minutes.
4. **Small per-instance defaults multiply.** A 30 s idle timeout looks harmless in one Nightscout instance; across 400
   it meant 1,400 logins per minute. Instance defaults should be reviewed with the fleet size in mind.
5. **Restarting the fleet resets memory, but it isn't a fix.** The restart released about 7 GiB of grown heaps and
   broke the loop. Instance memory growth still needs investigation.
6. **Inventory drifts.** 25 PM2 processes kept running for domains already deleted from the panel, and 26 running
   instances had no database at all.

## Diagnostic commands that helped

All are read-only, run over SSH as `ktomy` with `sudo` only where needed.

- Load, steal and memory history: `sar -q|-u|-r|-S|-W -f /var/log/sysstat/saDD`. Live: `vmstat 5`.
- CPU per category: `pidstat -u -r -C "node|mongod" 10 1`. Memory per category: PSS and swap from
  `/proc/*/smaps_rollup`.
- MongoDB: count `"Successfully authenticated"` and `"Slow query"` per minute in `/var/log/mongodb/mongod.log` (JSON
  lines). Connections: `ss -Htnp state established '( dport = :27017 )'` and `state time-wait`.
- cgroups: `/proc/<pid>/cgroup`, `/sys/fs/cgroup/system.slice/cgroup.subtree_control`, `cpu.weight`.
- nginx: status mix and request rate from `/var/log/nginx/access.log`; error types from `/var/log/nginx/error.log`.
